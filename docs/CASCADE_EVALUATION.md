# 로컬 → Jev 2단계 평가 (2026-10-13)

## 현재 구성과 최종 판정

새 실험은 `foundation_sec`, `qwen`, `jev`, `foundation_sec_then_jev`, `qwen_then_jev`를 선택합니다.

1. 로컬 모델이 공통 이메일 입력을 NORMAL / INJECTION / REVIEW로 판단합니다.
2. Jev는 동일 원문과 로컬의 유효한 판정 값을 받아 다시 검토합니다.
3. 두 단계가 성공하면 Jev 판정을 최종 결과로 사용합니다. 두 답이 다르다는 이유만으로 REVIEW로 변경하지 않습니다.
4. 어느 단계든 기술적 실패라면 ERROR/null입니다. 로컬 단계가 실패하면 Jev 요청을 생략합니다. 취소·미실행 상태도 정답으로 바꾸지 않습니다.

화면의 “로컬 정상 → Jev 인젝션”, “로컬 인젝션 → Jev 정상”은 **판정 변경 방향**입니다. 정답 라벨과 대조해야 개선인지 악화인지 알 수 있습니다. 사례 필터로 변경 전체·정상에서 인젝션·인젝션에서 정상만 조회할 수 있습니다. 개요에는 9가지 전이 조합의 건수를 표시합니다.

Jev 단독 대비 표는 같은 실험·같은 원본 입력 해시에서 양쪽이 모두 SUCCESS인 사례만 비교합니다. 오답→정답, 정답→오답, 정답→검토 필요, 검토 필요→정답을 구분합니다. Jev 단독이 미선택·실패이거나 입력이 다르면 비교 불가/N/A이며 자동으로 기준선 요청을 추가하지 않습니다. REVIEW는 탐지 성공으로 집계하지 않습니다.

## 입력·버전·재현성

- 로컬과 Jev 단독 기준: `email-injection-choice-v3` (2026-10-15 적용).
- 2차 질문: `email-injection-jev-review-v2`. 예비 판정과 일치한다는 사실 자체를 정당성의 근거로 삼지 않는다. 이전 단독 v2/재검토 v1 기록은 보존한다. 변경 및 검증은 [프롬프트 v3](PROMPT_V3.md) 참조.
- 최종 정책: `local-then-jev-final-v1`.
- 로컬의 내부 추론이나 추가 설명을 Jev에 전달하지 않습니다. 정답·출처·평가 메모·샘플 ID도 전달하지 않습니다.
- 검토 질문은 공통 분류 기준을 유지하면서 로컬 판정은 틀릴 수 있는 참고 정보이고, 원문을 확인해 판정을 유지하거나 수정하도록 지시합니다. Jev가 제공하지 않은 근거는 생성하지 않습니다.

Jev `state`의 JSON 문자열 내용:

```json
{
  "email": {"subject": "확인된 제목", "body": "기존 공통 입력 생성 결과"},
  "prior_assessment": {"decision": "NORMAL"}
}
```

위 `email`은 예시입니다. 실제로는 기존 공통 입력 생성기의 결과를 그대로 감싸며, Gmail 공통 입력에서 확인된 필드와 분석 본문도 기존 규칙을 따릅니다. 새 가상 이메일 필드는 만들지 않습니다.

2차 요청은 전체 상태의 `input_hash`, 원래 이메일의 `email_input_hash`, `prior_result_id`, 원본 `input_text`, 질문과 버전, 요청 크기, 응답·비용·시도 이력을 보존합니다. 최종 결과에는 두 `component_result_ids`, 1·2차 판정과 `decision_changed`, 각 단계 시간, 재사용 여부를 저장합니다. JSON/CSV 내보내기에 포함됩니다.

원본 이메일에는 기존 공통 입력 한도를 적용하고 자동 절단하지 않습니다. 추가 검토 래퍼의 바이트 수를 따로 기록합니다. Jev의 실제 서버 컨텍스트 한도는 확인되지 않아 null/미검증으로 유지합니다. 원문이 불완전하거나 한도 초과면 NORMAL로 처리하지 않습니다.

공식 [OpenRouter Decisions 요청 문서](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request)를 2026-10-13 재확인했습니다. `state`와 choice 질문의 `instructions`/`criteria`를 이용하며 기존 Decisions 엔드포인트·인증·응답 파서는 유지합니다. 이는 실제 모델이 해당 검토 과제에서 성능을 높인다는 검증이 아닙니다.

## 두 실행 방식과 비용

| 방식 | 로컬 1차 | Jev 2차 | 전체 2단계 시간 |
| --- | --- | --- | --- |
| 로컬 1차 재사용 (`reuse`) | 같은 실험의 응답 재사용 | 구성마다 새 호출 | N/A, 단계별 요청 시간만 표시 |
| 전체 순차 호출 (`live`) | 구성마다 새 호출 | 로컬 응답 후 새 호출 | 로컬 요청 시작부터 최종 판정까지 직접 측정 |

Jev 단독의 답을 2차 검토에 재사용하지 않습니다. 두 로컬의 판정이 같아도 Jev 요청은 별개입니다. Foundation-Sec와 Qwen은 동시에 로드하지 않으며 기존 해제 확인과 단일 작업 큐를 유지합니다.

5개 구성 모두 N건 실행 시, 모든 요청이 성공하고 재시도·워밍업·추가 설명이 없다는 조건에서:

- 재사용 방식: 로컬 2N회 + Jev 3N회. 5N개의 최종 평가 결과와 2N개의 추가 2차 요청 행을 저장합니다.
- 전체 순차 방식: 로컬 4N회 + Jev 3N회. 5N개의 최종 평가 결과와 4N개의 내부 요청 행을 저장합니다.
- **100건이면 두 방식 모두 Jev 300회**입니다. 비용은 실제 API 요청 행에서 한 번씩 합산하고 최종 결과 행에는 중복 청구하지 않습니다. 미확인 비용은 null입니다.
- 진행률의 “평가 항목 처리”는 내부 단계별 API 요청 횟수가 아닙니다. 숨겨진 의존 로컬 결과가 필요한 경우 그 항목도 작업 진행률에 포함됩니다.

## 기존 기록 호환성

과거 `foundation_sec_jev` / `qwen_jev`는 “기존 독립 결합”으로 표시합니다. 기존 결과·정책·스냅샷·비용은 수정하지 않으며 내보내기도 가능합니다. 새 실험 선택에서는 제외하고 해당 조합이 포함된 과거 실험의 재실행은 차단합니다. 새 방식은 새 실험으로 실행하세요.
